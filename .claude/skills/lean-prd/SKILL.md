# lean-prd — BML 기반 린스타트업 PRD 생성 및 사이클 관리 스킬

## 1. 핵심 철학 및 역할

전통적인 폭포수 PRD는 "무엇을 만들 것인가(기능 명세)"를 나열하지만, 초기 제품의 가장 큰 실패 원인은 "아무도 원하지 않는 기능을 완벽하게 만드는 것"이다.
이 스킬은 아이디어 한 줄을 입력받아 **가설(01·02) → 지표(05) → MVP·요구사항(03·04) → 실험(06) → 팀·기술스택(07·08) → 마일스톤(09) → 리스크·Pivot(10) → 로그·개요(11·00)** 순서로 계획하고, `docs/prd/` 아래 **12개의 개별 Markdown 파일**로 생성한다.

- **핵심 불변 규칙**: 모든 MVP `In` 기능, 핵심 지표, 실험, 마일스톤은 반드시 검증 가설 ID(`H#`)에 연결되어야 한다. 가설과 연결되지 않는 기능은 설령 초기 사용자 인터뷰나 피드백에서 요청되었더라도 낭비로 간주하여 `Out`으로 분류한다.
- **ID 네임스페이스 분리**: 문서 간 교차 참조의 모호성을 없애기 위해 6가지 접두사를 엄격히 구분한다.
  - 가설: `H1`, `H2`, ... (`01-problem-and-hypotheses.md`에서 정의)
  - 지표: `M1`, `M2`, ... 및 가드레일 `G1`, `G2` (`05-metrics.md`에서 정의)
  - 실험: `E1`, `E2`, ... (`06-experiment-plan.md`에서 정의)
  - 마일스톤: `MS0`, `MS1`, `MS2`, `MS3` (`M#` 지표와 혼동되지 않도록 반드시 `MS#` 사용)
  - Pivot 옵션: `P1`, `P2`, ... 및 트리거 `T1`, `T2`, ... (`10-risks-and-pivot.md`에서 정의)

## 2. 동작 모드 판별 (`generate` vs `cycle`)

| 모드 | 진입 조건 | 수행 작업 |
|---|---|---|
| **generate** | `docs/prd/`가 없거나 비어 있을 때, 또는 사용자가 새 아이디어로 PRD 초기 생성을 요청할 때 | 입력 질문(최대 5개) 확인 → BML 역순으로 12개 파일 생성 → 교차 참조 및 `validate_prd.py` 실행 |
| **cycle** | `docs/prd/11-bml-log.md`가 존재하고 사용자가 실험 측정값·BML 사이클 결과·Pivot/Persevere 판단을 요청할 때 | 실험 결과와 사전 임계값(`06` §3) 대조 → 결정 제안(사용자 승인) → `11-bml-log.md`에 `Cycle N` 추가 및 영향받는 파일만 선택적 갱신 |

## 3. `generate` 모드 상세 절차

### 1단계: 입력 수집 (질문은 한 턴에 최대 5개, 미응답 시 기본 가정 명시)

사용자가 아이디어 한 줄만 제공했을 때 여러 턴에 걸쳐 되묻지 않고 아래 **5가지 핵심 맥락을 단 한 번에** 질문한다:

1. **타깃 고객과 첫 10명**: 이 문제를 가장 심각하게 겪는 얼리어답터는 누구이며, 당장 이번 주에 연락 가능한 첫 10명은 어디에 있는가?
2. **현재 대안과 한계**: 타깃 고객은 지금 이 문제를 어떤 도구/수작업으로 해결하고 있으며 무엇이 가장 고통스러운가?
3. **팀 현황 및 가용 시간**: 참여 인원, 보유 기술 역량, 주당 투입 가능 시간(FTE)은 어떠한가?
4. **제약 조건**: 데드라인(총 기간), 월 가용 예산, 필수 사용 또는 사용 불가 기술/보안 제약이 있는가?
5. **사전 확보 데이터**: 기존 인터뷰, 설문, 프로토타입 사용성 테스트, A/B 테스트 등 이미 보유한 정량·정성 근거가 있는가?

- **기본 가정(Fallback Assumptions) 규칙**: 사용자가 "알아서 가정하고 바로 만들어줘"라고 답하거나 일부 항목을 비우면 작업을 멈추지 말고 합리적 기본 가정을 세운 뒤 **`00-overview.md` 상단 인용 블록과 `11-bml-log.md`의 `Cycle 0`에 반드시 `가정: ...` 형태로 명시**한다.
  - 기본값: `1인 팀(주 20시간 = 0.5 FTE)`, `예산 월 5만 원 이하(무료 티어 우선)`, `기간 8주(2주 × 4 마일스톤 MS0~MS3)`, `첫 10명 = 작성자 소속 연구실/학과/커뮤니티 지인`, `웹 기반 배포 우선`.

### 2단계: BML 역순 생성 순서와 그 이유

BML 사이클은 **Build → Measure → Learn** 순서로 **실행**되지만, 제품 기획(PRD 작성)은 반드시 **Learn → Measure → Build**의 **역순으로 설계**해야 한다(상세 근거: `references/bml-cycle.md` §1 참조):
1. 무엇을 배워야 하는지(**가설 H#**)를 먼저 정의하지 않고 기능을 정의하면 검증 목적 없는 기능 목록이 된다.
2. 가설이 참인지 판별할 **지표(M#)와 숫자 목표치**를 먼저 못 박아야, 그 지표를 수집하는 데 필요한 **최소한의 MVP(03)와 실험(06)** 범위가 도출된다.
3. MVP 범위가 확정되어야 이를 2주 내에 구현할 **팀(07)·기술 스택(08)·검증 마일스톤(09)·Pivot 안전장치(10)**를 과잉 설계 없이 짤 수 있다.
4. **`00-overview.md`를 가장 마지막에 쓰는 이유**: 개요와 Lean Canvas 9칸은 `01`~`10`에서 확정된 가설·지표·MVP·비용·채널의 요약본이다. 개요를 먼저 쓰면 뒤이어 구체화된 수치와 불일치가 발생하므로 반드시 맨 마지막에 작성한다.

### 3단계: 섹션별 작성 핵심 규칙 (위반 시 감점 방지)

- **01 가설**: `"우리는 [고객]이 [상황]에서 [행동]할 것이라고 믿는다. [M#]가 [목표 수치]이면 참이다."` 형식을 지킨다. 각 가설의 `불확실성`과 `치명도` 점수 산정 근거를 1줄씩 명시하며, 최고점(1순위 위험 가설)이 `MS0`의 검증 대상이 된다.
- **03 MVP 범위**:
  - `In/Out` 표의 모든 `In` 항목은 검증 가설 열에 `H#`가 있어야 한다(유일한 예외: 이벤트 로깅 등 `측정 장치` 또는 로그인/매니페스트 파서 등 `최소 동작 조건` — 이 경우 비고 열에 반드시 `측정 장치` 또는 `최소 동작 조건`을 명시).
  - **중요 (피드백 ≠ 가설)**: 사용자 인터뷰나 이전 과제 피드백에서 요청된 기능이라도 `"이 기능이 없으면 어떤 가설(H#)을 측정할 수 없는가?"`에 답할 수 없으면 `Out`으로 보내고, 비고에 피드백 출처와 재검토 조건(예: `MS2 이탈 사유 1위일 때 재검토`)을 적는다.
  - `In` 항목들의 합계 구축 기간은 **1인 환산 10 영업일(2주)** 이내여야 한다.
- **05 지표 & 06 실험**:
  - 모든 정의된 `H#`는 `05` §2 AARRR 표와 `06` 실험 설계, `09` 마일스톤에서 빠짐없이 참조되어야 한다.
  - 아직 가설이 없는 단계(예: 초기 Revenue `M4`)는 검증 가설 열을 `—`로, 목표 열을 `측정만`으로 기재한다.
  - `03` §4 MVP 성공 기준, `05` §2 목표(MVP), `06` §3 통과 임계값, `09` §2 종료 조건의 **숫자는 글자 그대로 일치**해야 한다.
- **07 팀 & 08 기술 스택**:
  - `07` §1 역할 표의 `투입 (FTE)` 열에는 반드시 숫자(예: `0.25`, `0.05`, `0`)를 기입하고, §4 의사결정 규칙에 Pivot 결정 시 `10` §2의 숫자 트리거 우선 원칙을 명시한다.
  - `08` §2 계층별 스택 표는 필수 7개 계층(`프론트엔드`, `백엔드`, `데이터`, `인증`, `호스팅`, `분석`, `CI/CD`)을 모두 포함하고 6열(`계층 | 선택 | 선택 근거 (MVP 관점) | 검토한 대안 | 월 비용 (예상) | 리스크 / 전환 조건`)에 빈칸이나 `—`가 없어야 한다. 가격·무료 한도는 `확인 필요: <공식 URL>`을 병기한다.
  - `08`에 최소 1개의 `ADR-1` 블록과 §4 `지금 하지 않을 것` 표(최소 3개 행 + 재검토 조건)를 포함한다.
- **09 마일스톤 & 10 Pivot**:
  - 마일스톤 헤딩은 반드시 `### MS0 — ...` ~ `### MS3 — ...` 4개 블록으로 작성하며, 각 블록 안에 `- 검증 가설: H#`, `- 종료 조건: <숫자 포함>`, `- Go: ...`, `- No-Go: ... -> P#`를 포함한다.
  - `10` §2 Pivot 트리거(`T1`~`T5`)의 조건 열에는 반드시 정량 숫자가 포함되어야 한다.
- **11 BML 로그**:
  - 초기 생성 시 `## Cycle 0 — 초기 가정` 블록을 작성하고, `## 검토 메모` 표는 사람이 직접 초안을 검토하며 채울 수 있도록(또는 검토 커밋에서 채우도록) 구분한다.

### 4단계: 교차 참조 자가 점검 및 검증 스크립트 실행

12개 파일 작성 직후 아래 명령어를 실행하여 형식 및 교차 참조 무결성을 검증한다:

```bash
python3 .claude/skills/lean-prd/scripts/validate_prd.py docs/prd
```

- `FAIL` 항목이 0개가 될 때까지 수정 후 재실행하며, 최종 통과 출력을 `docs/prd/VALIDATION.txt`에 저장한다.
- 스크립트가 검사하지 않는 **수치 일치성**(`03` 성공 기준 == `05` 목표치 == `06` 통과 기준 == `09` 종료 조건)을 모델이 직접 대조 확인한다.

## 4. `cycle` 모드 상세 절차 (`/lean-prd cycle`)

사용자가 실험 결과(예: `experiments/cycle-1/` 데이터, 설문/인터뷰 결과, A/B 테스트 지표)를 제공하면 다음 절차를 수행한다:

1. **입력 데이터 확인**: 검증 대상 가설(`H#`), 실험(`E#`), 측정된 주 지표(`M#`) 수치와 표본 크기(`N`), 가드레일(`G#`) 결과, 정성 피드백을 확인한다. 누락된 필수 수치가 있으면 한 번에 질문한다.
2. **사전 임계값 대조**: `06-experiment-plan.md` §3의 `통과 ≥` / `실패 <` / `회색 지대` 기준 및 `10-risks-and-pivot.md` §2의 트리거(`T#`)와 실측치를 나란히 비교한다.
3. **의사결정 제안 및 사용자 승인**:
   - **Persevere** (핵심 가설 통과 → 다음 마일스톤 진행 및 학습한 개선점 반영)
   - **Pivot** (`10` §3의 `P#` 옵션 실행 또는 Feature-level Zoom-in/Zoom-out 피벗)
   - **Kill** 또는 **재실험**
   - 스킬이 독단적으로 확정하지 않고 근거 1~2문장과 함께 제안하여 사용자의 확인을 받는다.
4. **선택적 파일 갱신 및 버전 업 (`v0.1 -> v0.2`)**:
   - `11-bml-log.md`: `## 사이클 요약` 표에 행을 추가하고 `## Cycle N — <날짜> — 대상 가설: H#` 상세 블록(가설 인용, Build, Measure, 사전 임계값, Learn, 결정, 변경된 섹션)을 기록한다.
   - 결정에 따라 영향받는 문서(`00`, `01`, `03`, `04`, `05`, `06`, `09`, `10` 중 해당 파일)의 본문과 상단 메타 블록(`버전`, `최종 수정`)을 갱신한다.
5. **재검증**: `python3 .claude/skills/lean-prd/scripts/validate_prd.py docs/prd | tee docs/prd/VALIDATION.txt`를 실행해 갱신 후에도 모든 규칙이 통과하는지 확인한다.

## 5. 절대 하지 말아야 할 것 (Anti-Patterns)

1. 12개 파일을 단일 파일로 병합하거나 필수 헤딩 문자열을 임의로 변경하지 않는다.
2. 템플릿 자리표시자(`{{...}}`)나 `TODO`, `TBD`를 본문에 남겨 두지 않는다.
3. 가설(`H#`) 연결이 없는 기능을 "있으면 좋은 기능"이라는 이유로 MVP `In`이나 MoSCoW `Must`에 넣지 않는다.
4. 기술 스택의 선택 근거를 "생태계가 커서", "인기가 많아서"처럼 일반론으로 적거나 대안·비용·리스크 열을 비워 두지 않는다.
